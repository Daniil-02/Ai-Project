## Частина 1. Google AI Studio (кроки 3, 7, 15)

### [№ 01] Первинний запит (Крок 3 — Схема від моделі за Заготовкою 1)
Ось перелік екранів і дані, які кожен показує:
1. Головна (/) — показує: загальна кількість учасників гільдії, кількість відкритих подій, усього подій у розкладі; картка наступного рейду (назва, дата й час, заповненість слотів основи та ліміт місць); картки найближчих рейдів (назва, статус набору, дата й час, слоти основи). Користувач нічого не вводить. Сутності: Учасник гільдії, Ігрова подія, Заявка на подію.
2. Склад гільдії (/members) — показує: таблиця учасників (нікнейм, клас персонажа, бойова роль, ранг у гільдії, статус активності). Користувач обирає фільтр бойової ролі (Усі, Танк, Хілер, ДПС). Сутність: Учасник гільдії.
3. Розклад подій (/events) — показує: список подій (складність/рівень рейду, назва, дата й час, зайняті слоти основи та максимум місць, статус набору). Користувач обирає фільтр статусу (Усі, Набір відкрито, Завершено). Сутності: Ігрова подія, Заявка на подію.
4. Нова подія (/events/new) — показує: форма створення події. Користувач вводить: назва події, дата та час, ліміт місць в основі, опис цілі рейду. Сутність: Ігрова подія.
5. Сторінка події (/events/[id]) — показує: статус набору, назва, рівень рейду, дата й час, опис, лічильник основного складу; список «Основний склад» (нікнейм, бойова роль, ранг); список «Резерв» (нікнейм, бойова роль); стрічка коментарів (автор, час, текст, лічильник скарг, позначка приховування). Користувач вводить: нікнейм і бойову роль для запису на рейд; дії переведення між основою і резервом, скасування заявки, завершення набору; нікнейм автора і текст коментаря, дії скарги та приховування коментаря. Сутності: Ігрова подія, Учасник гільдії, Заявка на подію, Коментар.

Запропонуй схему даних, що їх покриває. Для кожної таблиці вкажи, який екран її потребує. Для кожного поля вкажи, на якому екрані воно з'являється. Поля, які не використовує жоден екран, до схеми не включай.
Додаткові вимоги:
(а) База даних — PostgreSQL у хмарному проєкті Supabase.
(б) Сутності і зв'язки зі специфікації: Учасник гільдії (profiles), Ігрова подія (events), Заявка на подію (event_registrations), Коментар (event_comments).
(в) Обмеження теми: 3–5 таблиць, серед них хоча б один зв'язок «багато до багатьох»; користувачі зберігаються у власній таблиці profiles без посилань на таблиці входу.
(г) Формат відповіді: для кожної таблиці — таблиця з колонками «поле, тип, обов'язкове, екран»; окремо — перелік зв'язків із типом; SQL поки не писати.

**Відповідь моделі:**
Запропоновано 4 таблиці (profiles, events, event_registrations, event_comments) та загалом 29 полів:
- profiles (8 полів): id, nickname, character_class, role, rank, active_status, а також avatar_url (екран: жоден) і created_at (екран: жоден).
- events (9 полів): id, title, date_time, description, max_slots, status, а також created_at (екран: жоден), updated_at (екран: жоден), ai_tactics_plan (екран: жоден). Поле tier модель пропустила.
- event_registrations (5 полів): event_id, profile_id, combat_role, slot_status, а також registered_at (екран: жоден).
- event_comments (7 полів): id, event_id, author_nickname, comment_time, content, reports_count, is_hidden.
Зв'язки: events <-> profiles як M:N через event_registrations; events -> event_comments як 1:N.

### [№ 02] Первинний запит (Крок 7 — Порада моделі й SQL першої міграції)
Контекст: Вебзастосунок Next.js, хмарний проєкт Supabase, робота ведеться в GitHub Codespaces; таблиць у базі ще немає.
Вхідні дані: Остаточна схема з 4 таблиць (profiles, events, event_registrations, event_comments — 24 поля) та зв'язки M:N і 1:N.
Завдання: (1) Одним-двома реченнями порадь, як завести цю схему в базу проєкту; (2) Дай SQL, що створює таблиці.
Обмеження до SQL: первинні ключі uuid primary key default gen_random_uuid(), у таблиці зв'язку event_registrations складений первинний ключ (event_id, profile_id); посилання через references ... on delete cascade; для обов'язкових текстових полів not null check (length(trim(...)) > 0); для кожної таблиці enable row level security та тимчасова політика pr4_temp_all для anon, authenticated; без drop і без тестових даних.
Формат: спершу порада, потім SQL одним блоком.

**Відповідь моделі:**
Порада: «Відкрийте розділ SQL Editor у панелі керування Supabase, вставте наведений нижче SQL-скрипт у нове вікно запиту та натисніть кнопку Run для створення таблиць».
Надано SQL створення 4 таблиць із enable row level security та політиками pr4_temp_all, але без рядків grant для ролей.

### [№ 09] Первинний запит (Крок 15 — Друга міграція за Заготовкою 2)
Ось поточна схема і застосовані міграції: [вміст файлу supabase/migrations/20261023201226_create_schema.sql та docs/pr4-migrations.txt]. Мені потрібно додати необов'язкове текстове поле ai_tactics (text) у таблицю public.events для відкладеної функції «Генерація тактичного опису рейду через ШІ». Запропонуй міграцію, яка вносить цю зміну і зберігає наявні дані. Перестворення таблиць і видалення даних не пропонуй. Поясни, що станеться з наявними рядками щодо нового поля.
Доповнення:
(а) У таблиці public.events вже є 3 рядки даних, міграція застосовується командою npx supabase db push.
(б) Перша міграція не редагується, новий файл містить лише команду зміни схеми.
(в) Формат: SQL одним блоком, потім одне-два речення пояснення про наявні рядки.

**Відповідь моделі:**
```sql
alter table public.events add column ai_tactics text;
```
Пояснення: Оскільки нове поле ai_tactics додається командою alter table ... add column без обмеження not null, таблиця не перестворюється, усі 3 наявні рядки повністю зберігаються, а в колонці ai_tactics для них автоматично встановлюється значення NULL.
